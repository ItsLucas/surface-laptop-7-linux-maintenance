## 当前维护基线（2026-09-14收尾）

当前默认镜像已支持Wi-Fi、触控板和GTCH SPI触摸屏；源码补丁集为3个内核补丁、2个iptsd源码补丁及1个打包补丁。iptsd版本3.1.0+sl7.2-1。原Ubuntu和原组合镜像保留；GRUB有5秒回退菜单，当前完整功能条目ID仍沿用sl7-spi-touchscreen-test。

以后每次Ubuntu更新都先检查上游是否已覆盖这些具体改动，再对新Ubuntu源重新移植剩余补丁，避免重复应用。系统更新不会自动重建本地自定义内核；不要把旧模块复制进新内核或关闭Secure Boot解决验签问题。

新版本需独立kernel release、/lib/modules目录及启动镜像路径；用现有受信任密钥签模块和EFI，核对ABI/证书/设备树后单次启动。验收至少包括Wi-Fi硬开关和正确MAC、联网、蓝牙、触控板指尖/拇指/轻触/物理点击/滚动、触摸屏与Secure Boot。睡眠恢复和功耗另行验收；当前热图缺失停顿不能被写成已解决。

只有验收后、按用户授权再改默认；保留已知可用版本及匹配initrd。iptsd升级必须保留/etc/iptsd.d中的本机校准，并使用最终打包脚本；如果以后udev规则确需重探测，应协调服务停止/启动顺序，不能照搬旧的无条件升级探测。

以下是之前整理的具体构建、检查及并存打包步骤，结合本节的完整补丁集执行。

**采用“官方包继续更新，本地组合内核并存试启动，通过后再切默认”的流程。**

当前可靠基线是 Ubuntu `7.2.0-5.5` + 本地硬件补丁，运行版本 `7.2.0-5-sl7`。它已经固定为默认，因此安装更新的官方内核不会自动让当前运行的本地内核获得安全修复。保留官方内核元包是获取后续基线和回退版本的渠道。

**更新节奏与边界**

- 平时每周检查 APT 内核候选版本和 [Ubuntu 安全公告](https://ubuntu.com/security/notices)；有影响本机的高危内核修复时优先移植和验证。
- Ubuntu 26.10 目前为开发版，包名、配置和工具链可能继续变化。大版本发行升级单独安排，不把它和日常内核换版混在一次操作中。
- 继续保留 `linux-generic-hwe-26.04`、`linux-image-generic-hwe-26.04`、`linux-headers-generic-hwe-26.04`。当前没有 apt hold；本次整理没有新增 hold、定时器、自动安装或重启任务。
- 保留当前已验证的本地内核、最近官方内核，以及升级前的安装包与补丁。清理旧包先预演，并避免自动删除唯一可用回退版本。
- iptsd、校准、UEFI MAC 服务与内核分别维护。除非 ABI、依赖或上游修复需要，不因每次内核更新重编 iptsd。

先由用户正常刷新 APT 缓存，再运行归档的只读检查工具：

```bash
sudo apt update
python3 tools/check-kernel-update.py
```

工具本身不联网刷新缓存、不安装软件、不改启动项。它会比较当前归档基线 `7.2.0-5.5` 与元包候选版本；升级并验收后，需要给新归档更新这个基线。

**每次更新的具体流程**

1. **记录候选版本。** 获取精确的 Ubuntu source 包、对应官方 config、buildinfo/Canonical 公钥和撤销列表。记录包版本、下载来源与哈希。当前 APT 配置只有二进制源；若改用 `apt source`，先配置对应的 deb-src，或继续使用 Ubuntu 的版本化 `linux-source-*` 二进制源码包。
2. **开独立构建目录。** 从候选官方配置开始执行 `olddefconfig`，核对新增/删除的选项及编译器/Rust/bindgen 要求。保留当前源码和输出，不在当前可用版本上原地覆盖。新 release 必须唯一，例如某个新 Ubuntu ABI 后附加 `-sl7.1`；即使 Ubuntu ABI 没变，只要本地补丁或签名信任变化，也递增本地编号。
3. **逐组审阅补丁。** 先尝试零 fuzz 应用内核 series；失败时审阅上游变化并三方移植。不能自动丢掉应用失败的补丁，也不能把“能应用”当作运行正确。核对 ath12k 模块拆分、rfkill 语义、GENI/GPI API、HID 生命周期和 DT 绑定是否改变。
4. **构建与签名。** 先编译相关 DTB/对象，再完整构建独立版本。模块完成 strip 后签名、再压缩；新内核内建现有模块公钥。用新的匹配 Stubble 输入构建携带 DTB/HWID 的镜像，对内外两层 PE 验签。保持 `efi=noruntime` 与 Secure Boot；现有两张 MOK 未变且私钥仍在时无需重复登记。
5. **制作可并存包。** 使用下文的版本化布局，先做依赖安装预演。沿用 dracut，不让依赖求解替换当前生成器。initrd 应包含板级固件覆盖、QSPI/GPI/HID 模块，并保持模块签名字节不变。
6. **审核后安装，单次测试。** 在具体产物、哈希、验签及回退方案都准备好后，按用户要求取得危险操作批准。安装新包时维持当前正常版本为默认；`grub-reboot <新版本唯一 entry ID>` 只安排下一次试启动，实际重启由用户保存工作后进行。
7. **验收。** 检查新 `uname -r`、Secure Boot/lockdown、模块信任、Wi-Fi 地址/连接/路由、触控板指尖/拇指/点击/双指、蓝牙鼠标。另安排至少一次休眠恢复，并注意显示、USB、供电方面是否回归。新内核失败时，重新启动选择旧的已验证本地内核；官方内核是另一条回退路径。
8. **通过后切默认。** 获准后仅修改独立的 `zz-sl7-local-kernel.cfg` 指向新 ID，运行 `update-grub`。归档源码版本、series、config 差异、签名、包和验收记录。保留上一版，稳定使用后再计划清理。

Ubuntu 官方构建说明也要求修改本地版本以避免与原内核冲突；本机另外需要设备树打包和签名验证。[Ubuntu 内核构建文档](https://documentation.ubuntu.com/kernel/how-to/develop-customise/build-kernel/)

**下次打包前必须改的固定路径**

当前 `linux-image-7.2.0-5-sl7` 含有以下共享名称。直接把它复制成另一个 package name 安装，会碰到文件所有权冲突或覆盖旧启动项：

| 当前路径/标识 | 下一个并存版本建议 |
|---|---|
| `/etc/grub.d/43_sl7_combined_kernel` | `/etc/grub.d/43_sl7_<release>`，entry ID 使用 `sl7-<release>` |
| `/usr/share/sl7-kernel/` | `/usr/share/sl7-kernel/<release>/` 保存该版本公钥副本 |
| `sl7-iptsd-coldplug.service` 且 ConditionKernelVersion 固定 | `sl7-iptsd-coldplug-<release>.service`，仅在对应内核运行 |
| postinst/prerm/postrm 中的固定 release | 全部由同一个版本变量生成 |
| 原签名/验证脚本中的路径与 `RELEASE` | 使用新构建目录、Module.symvers、sign-file 和 release |

`/boot/sl7/<release>/` 与 `/lib/modules/<release>/` 已按版本分离，继续保留。默认选择文件不放入每个内核包自动修改；只有实机验收后才切换。

今后版本多了，可以另做 `sl7-platform-support` 公共集成包统一拥有不随版本变化的文件；这需要明确迁移旧包文件所有权。本次只制定方案，没有修改当前可用的包布局，也没有安装一个虚构的通用升级器。

**各组补丁的退出条件**

- **rfkill workaround：** 上游为本机提供正确解决方案后，在保留回退的候选内核中去掉 workaround，验证 hard block、软件无线开关、实际连接和恢复。不能仅凭补丁不再应用就删除。
- **QSPI/HID/DT：** 判断内核是否已经同时包含控制器、DMA、HID transport 和 Romulus13 wiring。只有这几层都可用且实测通过，才逐组减少本地补丁。
- **iptsd fork：** 用归档的 16 文件完整差异检查新上游是否覆盖按键、去抖、跟踪和恢复行为；发行版 iptsd 版本更高不等于具备同样功能。
- **board-2 override：** `firmware/updates` 会持续遮盖更新后的发行版文件。每次 linux-firmware 或 Windows 提取固件更新后，检查新官方板级容器是否已有正确名称和数据；确认可用后再撤掉旧 override 并重建目标 initrd。
- **UEFI MAC：** 若以后内核/发行版已读取正确地址，验证当前地址、关联时地址及重启稳定性，再移除用户态补偿。现阶段不要改为使用驱动报告的 `permanent`，因为它曾是临时生成地址。
- **校准：** 保留当前 `/etc/iptsd.d/91-calibration-045E-0C77.conf`；只有检测算法、几何信息或手感变化时重采，覆盖时先备份。

**签名与恢复原则**

模块私钥在 `/var/lib/shim-signed/mok/sl7-wifi/MOK.priv`，启动私钥在 `/var/lib/shim-signed/mok/sl7-kernel/BOOT.priv`。公开证书已归档，私钥没有放进源码包。长期维护应由用户选择加密、离线的私钥备份方式；如果丢失私钥，已签好的当前包仍可使用，但新的构建需要新密钥和新的 MOK 登记。

UEFI/BIOS 更新、shim/GRUB 更新可能影响 MOK 或 SBAT 验证，操作后复核信任状态。module-only 证书不能替代启动镜像证书；保持这一区分。[Ubuntu Secure Boot 文档](https://documentation.ubuntu.com/security/docs/security-features/platform-protections/secure-boot/)

本机 mokutil 0.7.2 的 `--test-key` 对“已登记”曾返回 1，不能把 exit code 0 硬编码为唯一成功判据；核对输出、证书指纹与实际启动验证。以后版本行为可能改变。

整个升级过程保留 Secure Boot 与官方回退路径。没有必要重启到 `efi=runtime` 重复旧试验，也不要通过禁用签名检查来掩盖构建或信任问题。


**用户后续澄清与清理：** 鼠标此前由用户主动关机，等待超时符合这一情况，不能据此认定蓝牙故障。用户不再需要鼠标自动重连，已于本次归档中清理 `sl7-mouse-connect.service` 和对应脚本，保留正常蓝牙功能。历史文件移至 `history/retired-mouse-autoconnect/`，不在当前系统配置快照内。
